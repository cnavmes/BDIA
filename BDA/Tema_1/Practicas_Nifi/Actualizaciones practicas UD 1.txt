Actualizamos la versión de Java (Solo lo actualizamos en Nifi):

- Instalamos Java 21 en paralelo (sin tocar el sistema)

    sudo apt update
    sudo apt install openjdk-21-jdk

- Comprobamos la ruta:

    ls -d /usr/lib/jvm/java-21-openjdk-amd64

- Mantenemos Java 11 como predeterminado en el sistema

    sudo update-alternatives --config java
    sudo update-alternatives --config javac
    Selecciona la entrada de Java 11.

- Verificamos:
   
    java -version   # debe mostrar 11

- Configuramos NiFi para usar Java 21

    sudo nano /opt/nifi/bin/nifi-env.sh

    JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64

En la versión 2.6. de Nifi no existen las plantillas. Para obtener el JSON haremos:

1. Creamos un process group con los procesos.

2. Sobre el grupo, le damos al botón derecho. En el menú contextual seleccionaremos la descarga del "Flow Definition".

3. Añadimos el nuevo process group e indicamos la plantilla con la que queremos trabajar.

Como en la versión 2.5.0. no viene por defecto la gestión de HDFS, instalamos los elementos nar.

1. Descargamos los NARs

    wget https://repo1.maven.org/maven2/org/apache/nifi/nifi-hadoop-nar/2.5.0/nifi-hadoop-nar-2.5.0.nar
    wget https://repo1.maven.org/maven2/org/apache/nifi/nifi-hadoop-libraries-nar/2.5.0/nifi-hadoop-libraries-nar-2.5.0.nar

2. Copiamos ambos en el directorio lib de NiFi

    sudo cp nifi-hadoop-*.nar /opt/nifi/lib/

    /opt/nifi/bin/nifi.sh restart

En la práctica 7 no hace falta ZooKeeper. Descargamos Kafka 4.1.0.

Motivo:

Hasta la versión 2.7, Apache Kafka dependía de ZooKeeper para gestionar la metadata del clúster. ZooKeeper almacenaba información sobre los brokers activos, 
los tópicos, las particiones y sus réplicas, además de coordinar la elección de líderes y detectar fallos de nodos mediante znodes efímeros. En la práctica, 
ZooKeeper actuaba como un servicio externo de coordinación imprescindible para que Kafka pudiera operar en alta disponibilidad y con tolerancia a fallos.

Con la llegada del modo KRaft (Kafka Raft Metadata mode), Kafka ya no necesita ZooKeeper. Ahora la metadata se guarda en un log replicado dentro de los propios 
brokers, y el consenso se mantiene mediante el algoritmo Raft. Esto simplifica la arquitectura, elimina la dependencia de un sistema externo y mejora la 
escalabilidad en clústeres grandes. Desde Kafka 3.3 KRaft se considera estable para producción y en las versiones actuales ZooKeeper ya está en proceso de 
eliminación definitiva.

Práctica 7. Configuración inicial de Kafka.

1. Creamos el directorio de metadatos

    sudo mkdir -p /opt/kafka-data
    sudo chown -R hadoop:hadoop /opt/kafka-data

2. Editamos la configuración server.properties

    En $KAFKA_HOME/config/server.properties, asegúrate de que estén estas líneas (mínimo para un nodo en KRaft):

    process.roles=broker,controller
    node.id=1

    listeners=PLAINTEXT://:9092,CONTROLLER://:9093
    advertised.listeners=PLAINTEXT://localhost:9092
    controller.listener.names=CONTROLLER
    listener.security.protocol.map=PLAINTEXT:PLAINTEXT,CONTROLLER:PLAINTEXT
    inter.broker.listener.name=PLAINTEXT

    # Quorum KRaft (node.id@host:puerto_del_listener_CONTROLLER)
    controller.quorum.voters=1@localhost:9093

    # Carpeta de logs y metadatos
    log.dirs=/opt/kafka-data

3. Generamos el cluster.id

    UUID=$($KAFKA_HOME/bin/kafka-storage.sh random-uuid)
    echo $UUID

    Esto devuelve algo como:

    aBCdEfGhIjKlMnOpQrStUv

4. Formateamos el almacenamiento

    $KAFKA_HOME/bin/kafka-storage.sh format -t $UUID -c $KAFKA_HOME/config/server.properties

5. Verificamos el meta.properties

    cat /opt/kafka-data/meta.properties

    Deberías ver algo así:

    version=1
    cluster.id=aBCdEfGhIjKlMnOpQrStUv
    node.id=1

6. Arrancamos Kafka

    kafka-server-start.sh $KAFKA_HOME/config/server.properties &
	
    Para pararlo es kafka-server-stop.sh
